## これは何か

ブラウザで動く光の粒子作品です。その裏では、百万個の粒子が互いに引き合う**本物の重力多体シミュレーション**を GPU で解いています。

**HTML 1ファイル**で完結しています。外部ライブラリなし、ビルドツールなし、three.js なし。開けば動きます。

| 操作 | 起きること |
|:--|:--|
| **言葉を打つ** | 百万個の粒子がその形へ飛んでいく。英字・ひらがな・漢字・絵文字、どれでも描ける |
| **画面をなぞる** | 粒子が散り、渦を巻き、また元の形に戻る |
| **「放つ」を押す** | 粒子を留めていたバネが外れ、粒子どうしが引き合いはじめる。言葉は自分の重さでたわみ、いくつもの塊に分かれ、塊の間に糸のような構造（フィラメント）を引き、最後は回転する円盤になる。**「戻す」**で元の形に戻る |
| **形を選ぶ** | 球・銀河・結び目・波・環・ハート・螺旋の7種と、待機状態の光の雲「蛍」。形に対しても「放つ」が使える |

同じ言葉を二度放っても、同じ崩れ方はしません。録画の再生ではなく、その場で計算しているからです。

## 動かす

- **オンライン** — [futurecortexlabs.github.io/FCTX_HOTARU](https://futurecortexlabs.github.io/FCTX_HOTARU/)
- **手元で** — リポジトリを clone して `index.html` をブラウザで開くだけ。サーバもインストールも不要です。
- **動作が重いとき** — URL の末尾に `?n=65536` を付けると、粒子数を 65,536 個に固定できます。

WebGL2 に対応したブラウザ（最新の Chrome・Edge・Safari・Firefox）が必要です。

### ソースからビルドする

```bash
node build-hotaru.js
```

```bash
npm test
```

ビルドは [`hotaru/`](hotaru) の5つのモジュールと [`web/`](web) のページ本体を連結し、`index.html` を書き出します。テストは 5,335 件のチェックを実行します。必要なのは Node 18 以上だけです。`puppeteer-core` はブラウザ検証ハーネス専用の開発依存で、インストール済みの Chrome を操作するために使います。

## 仕組み

毎フレーム、次の処理がすべて GPU 上で走ります。

```
位置・速度テクスチャ（RGBA32F, 1024x1024 = 1,048,576 粒子）
        |
        +- 1. 堆積    各粒子の質量を 64^3 の格子に足し込む
        |             （格子は z 方向の断面を 512x512 の1枚のテクスチャに並べて保持）
        +- 2. 求解    ポアソン方程式 grad^2 phi = 4 pi G rho を解いて重力ポテンシャルを得る。
        |             Chebyshev 加速の反復を 24 回、前フレームの解から始める
        +- 3. 力      ポテンシャルの勾配 -grad(phi) を各粒子の位置で読み取る
        +- 4. 積分    1つのシェーダで位置と速度を同時に更新（マルチレンダーターゲット）
        +- 5. 描画    描画命令は1回だけ。各点は gl_VertexID から自分の粒子を読む
        +- 6. 仕上げ  自動露出 → ブルーム → ACES トーンマッピング
```

CPU 側に粒子の配列はなく、頂点バッファもありません。画面全体が `drawArrays(POINTS, 0, 1048576)` の1回で描かれ、各頂点は自分の番号を使ってテクスチャから粒子の位置を読みます。

露出は自動です。描画結果を1ピクセルまで平均し、時間方向になめらかにしてから明るさの倍率に使います。崩壊の途中で密度が百倍ほど変わるため、手で露出を合わせることはできません。

## 自己重力は本物

百万個の粒子すべての組み合わせで引力を直接計算すると、1フレームあたり 10¹² 回になり不可能です。そこで、宇宙論の N 体シミュレーションと同じ **Particle-Mesh 法（PM 法）**を使います。

1. **堆積** — 各粒子の質量を、3次元格子のいちばん近いセルに足し込む。
2. **求解** — 格子上でポアソン方程式を解き、重力ポテンシャルを求める。端が反対側につながった（周期境界の）箱では、平均密度を差し引かないと解が存在しません。物理学ではこれを「Jeans の swindle」と呼びます。
3. **微分** — ポテンシャルの傾きから力を求め、各粒子の位置へ補間して戻す。

### なぜ Chebyshev 法なのか、「24回」はどこから来たのか

**要点：** 教科書どおりの解き方（ヤコビ法）では、力の誤差を 1% に抑えるのに毎フレーム約 210 回の反復が要ります。同じ計算に Chebyshev 加速をかけると 24〜26 回で届くので、Hotaru は 24 回にしています。この数字は勘ではなく実測です。

ヤコビ法は、重力にとっていちばん大事な「大きなスケールの構造」ほど収束が遅いという弱点があります。そこで反復回数を勘で決めるのではなく、このリポジトリには**厳密な CPU 参照実装** [`hotaru/pm.js`](hotaru/pm.js)（3次元 FFT で同じ方程式を正確に解くもの）を用意し、[`test/pm.test.js`](test/pm.test.js) が「GPU で何回反復すれば参照解に追いつくか」を測っています。

下表は、各粒子にかかる力の誤差を 3% / 1% まで下げるのに必要な、1フレームあたりの反復回数です。毎フレーム前フレームの解から始めています。比較相手は「同じ離散方程式」の厳密解なので、反復を途中で打ち切ったことによる誤差だけを見ています。

| 格子 | ヤコビ → 3% | ヤコビ → 1% | Chebyshev → 3% | Chebyshev → 1% |
|:--|--:|--:|--:|--:|
| 32³ | 約70 | 128超 | **約9** | **約15** |
| 64³ | 約94 | 約210 | **約10** | **約26** |
| 128³ | 約158 | 256超 | **約15** | **約42** |

<details>
<summary><b>数式での説明</b></summary>

遅さは調整不足ではなく、作用素のスペクトルそのものに由来します。ヤコビ法の1回の掃引は、最も遅いモードの誤差を `(2 + cos(2π/N))/3` 倍 — 64³ なら 0.9984 倍 — にしか縮めません。しかも φ<sub>k</sub> ~ ρ<sub>k</sub>/k² なので、そのモードこそがポテンシャルの大部分を担っています。同じ掃引に Chebyshev 半反復法をかけると、1回あたり 0.9449 倍になります。条件数の平方根ぶんの高速化で、完全に並列のまま、赤黒ガウス・ザイデル法のように z 断面テクスチャの中で市松模様の順序を考える必要もありません。

ステンシルは同じで、書き戻す値だけが変わります。

```
x[k+1] = alpha[k] * (c1 * sweep(x[k]) - c2 * x[k]) - beta[k] * x[k-1]
```

ピンポンバッファが2枚から3枚になるだけです。`beta[0] = 0` なので、初回は `x[k-1]` を読みません。`c1`・`c2` は格子サイズだけ、`alpha`・`beta` は格子サイズと反復番号だけで決まるので、反復ごとに float のユニフォームが2つ、最初に一度計算すれば済みます。

平均密度の差し引きは省略できず、しかもコストはかかりません。生の密度のまま反復すると、箱の中に正味の質量があるため、毎回ポテンシャルの平均が一定量ずつずれ続けます（32³ で200回反復後に −0.409。予測値と 1e-9 の精度で一致）。float32 では、本当に必要な場が大きな数の下位ビットに埋もれてしまいます。この平均は GPU で集計する必要もありません。各粒子はちょうど 1.0 ずつ質量を書き込むので総質量は正確にわかっており、平均は `totalMass / L³` で求まります。

</details>

> **なぜ実測する価値があったのか。** 反復回数が足りないとき、ソルバは目に見えるノイズを出しません。多くのセルにわたって滑らかでそろった誤差を出します。もっともらしく見えるのに、静かに間違っている場です。画面を眺めていても気づけません。

### 本当に落ちているのか

粒子が画面いっぱいに広がると、縮んでいるのか膨らんでいるのかは目では区別できません。そこで [`tools/probe-gravity.js`](tools/probe-gravity.js) が GPU から粒子の位置を読み戻し、雲の半径を直接測ります。初期状態は半径1の静止した薄い球殻で、ノイズと減衰を切り、重力だけが働くようにしています。

```
  t=0   rms 1.002
  t=3   rms 0.887   収縮
  t=5   rms 0.654   収縮
  t=7   rms 0.168   収縮
  t=8   rms 0.255   膨張   <- 中心を通り抜けて跳ね返る
```

理論値は 6.6 秒です。薄い球殻の各部分は、殻自身の重力を実効的に GM/2 として受けるので、落下時間は (π/2)√(R³/GM) = 6.64 秒（GM = 0.056）。実測は 7 秒でした。摩擦のない崩壊は中心を行き過ぎて跳ね返る — 教科書どおりの振る舞いです。

## 既知の限界

近似を隠すデモは信用に値しないので、正直に書いておきます。

- **重力モードには物理ではない制限が3つあります。** 加速度の上限 6.0（`forceClamp`。崩壊の中心付近では実際に効いています）、速度の上限 8.0、そして放った後の速度が毎秒約 8.6% ずつ減る減衰（`damp: 0.9985`）です。計算を安定させ、見た目を整えるためのもので、物理ではありません。上の落下時間の測定は、この減衰を切った状態で行っています。
- **質量は最寄りのセルに書き込み、力は三重線形補間で読み取っています。** この2つが厳密には対応していないため、各粒子はわずかに自分自身からの力を受けます。直すには（CIC 法での堆積）、点は1ピクセルにしか書けないので描画を8回に増やす必要があり、映像作品としては見合わないと判断しました。参照実装によれば、力が信頼できるのはおよそ4セル以上離れた粒子どうしです。
- **シミュレーションの箱は端が反対側につながっている**ため、遠くにある雲の「写し」からのわずかな引力が残ります。箱は雲の数倍の大きさなので影響は小さいものの、ゼロではありません。
- **半径 2.4 より外では、粒子を引き戻す人工的な力**が働きます。箱の端を越えて反対側に回り込まないようにするための処置で、物理ではありません。
- **32bit float のテクスチャに加算するには `EXT_float_blend` 拡張が必要です。** 無い環境では質量の格子が 16bit float になり、1セルに約 2,048 個を超える粒子が集まると正確に数えられなくなります。
- **依存ゼロは自慢ではなく制約です。** ひとつでも足せば、誰でも開ける1ファイル配布ができなくなります。
